# 十档播客定期追踪 · 转录 · 翻译 · 双站点发布系统

## 一、项目目标

定期（全自动）追踪 10 档播客的更新，将新一集音频转为文字，非中文内容翻译为中文，
整理成可读文章后，同时发布到两个独立目的地：

1. **现有博客**（Hugo/Hexo）：按发布时间混排的常规文章
2. **新网站**（播客专属站点）：按节目分栏目，每个栏目下按时间列出该节目所有集数

两边发布**完整内容**（非索引跳转关系），内容生成一次，分发两份。

---

## 二、播客数据源

10 档播客统一用一份配置文件描述，不写死在代码里，方便以后增减：

```yaml
# config/shows.yaml
shows:
  - name: "示例播客A"
    slug: show-a              # 用作新网站栏目路径 /show-a/
    platform: youtube         # youtube / xiaoyuzhou / apple / rss
    identifier: "https://www.youtube.com/@xxxx"
    language: en              # en / ja / zh ... 非zh会触发翻译
  - name: "示例播客B"
    slug: show-b
    platform: xiaoyuzhou
    identifier: "https://www.xiaoyuzhoufm.com/podcast/xxxx"
    language: zh
  # ... 共10档
```

**音频获取采用"解析器插件"模式**，按以下顺序尝试，任何一步失败就降级到下一步：

1. 平台专属解析器（YouTube 用 yt-dlp；小宇宙解析分享页拿直链；Apple Podcasts 反查 RSS）
2. 通用：iTunes Search API 按节目名找到 `feedUrl`，从 RSS 定位具体集数
3. yt-dlp 通用提取器兜底
4. 都失败：记录日志，跳过该集，不阻塞其他节目

新增第 11 档播客时，只需在 `shows.yaml` 加一行 + 必要时加一个平台解析器函数。

## 三、处理流程（单集）

```
1. 检测新集数
   对比 RSS/平台最新集数 与 state/processed_episodes.json 中的记录，
   决定是否为"新集数"

2. 下载音频 → audio/{show-slug}/{date}-{episode-slug}.mp3

3. 语音转文字
   本地 faster-whisper，模型 small 或 medium（见"六、限制"）
   源语言按 shows.yaml 中 language 字段指定，输出带时间戳的原始转录

4. 翻译 + 整理（用 Claude API 一次完成）
   - 若 language != zh：翻译为中文（保留专有名词处理的语境判断）
   - 去除口语填充词、合并自然段落
   - 按话题自动分小标题
   - 生成 200 字以内摘要
   - 保留关键时间戳
   - 附来源信息：播客名、期数、原始链接、发布日期

5. 生成两份 markdown（同一份整理内容，两套 front matter）
   - 博客：content/posts/{date}-{episode-slug}.md
   - 新网站：content/{show-slug}/{episode-slug}.md

6. 更新 state/processed_episodes.json，标记该集已处理

7. git commit + push（两个站点各自的仓库或目录）
```

## 四、自动化运行（GitHub Actions）

```yaml
# .github/workflows/daily-check.yml
# 每天定时触发，遍历 shows.yaml 逐个检查更新
# 触发方式：schedule (cron) + workflow_dispatch（保留手动触发入口方便调试）
```

关键设计点：

- **状态文件入库**：`state/processed_episodes.json` 提交进 git 仓库本身，
  这样每次 Actions 运行都能读到"上次跑到哪了"，不依赖外部数据库。
- **单集失败不影响整体**：某一集转录/翻译出错时记录日志、跳过，
  不让整个 workflow 失败导致其他 9 档播客也没更新。
- **提交信息规范化**：如 `feat: 发布《示例播客A》第32期`，方便后续追溯。

## 五、目录结构建议

```
podcast-pipeline/
├── config/
│   └── shows.yaml
├── state/
│   └── processed_episodes.json
├── scripts/
│   ├── check_new_episodes.py
│   ├── resolvers/              # 平台解析器插件目录
│   │   ├── youtube.py
│   │   ├── xiaoyuzhou.py
│   │   ├── apple_podcasts.py
│   │   └── fallback_ytdlp.py
│   ├── transcribe.py
│   ├── translate_and_clean.py   # 调用 Claude API
│   ├── generate_blog_post.py
│   ├── generate_site_entry.py
│   └── publish.py
├── audio/                       # 临时文件，.gitignore
├── transcripts/raw/             # 原始转录稿留存（含原文语言版本）
├── site-blog/                   # 或指向已有博客仓库
├── site-podcast-directory/      # 新网站源码
└── .github/workflows/
    └── daily-check.yml
```

新网站（播客目录站）用 Hugo 的 section/taxonomy 天然契合"每档播客一个栏目"的需求：
每个 `slug` 对应一个 section，该 section 下的所有文章按日期倒序即为该节目的集数列表。

## 六、需要注意的限制

- **GitHub Actions 免费 runner 只有 CPU，没有 GPU**。用 faster-whisper 的
  `medium` 模型转录 1 小时音频大致要 15–30 分钟（视机型浮动），
  10 档播客同一天都更新的极端情况下要留意单次 workflow 是否会跑很久
  （GitHub Actions 单个 job 上限 6 小时）。如果常态化更新频率高、单集较长，
  可以考虑：模型换成 `small` 换取速度，或对转录这一步改用云端语音识别 API
  （更快但要花钱）。
- **Claude API 成本**：翻译 + 整理这一步按 token 计费，10 档播客持续运行下来
  是稳定的月度开销，值得在决定模型档位（如是否用更便宜的模型做翻译）时考虑。
- **版权**：两个站点都公开发布完整逐字稿/翻译内容，建议保留清晰的来源标注
  （播客名、期数、原始链接），这是目前能做到的最基本的自我保护措施。

---

## 七、建议的实现顺序

不建议一次性要求 Claude Code 把整套系统写完，容易调试困难。建议分阶段：

1. **单集手动流程跑通**：给定一个链接，手动执行"下载→转录→翻译整理→生成
   markdown"，先确认转录质量、翻译质量、文章格式都满意
2. **接入 1 档播客的自动检测**：新集数检测 + state 文件逻辑跑通
3. **扩展到全部 10 档**，跑通"平台解析器插件"模式
4. **接入双站点发布**（先各自 push 到位，再检查两边站点是否正确渲染）
5. **最后接入 GitHub Actions 定时触发**，改为全自动

每个阶段都能独立验证，出问题时也容易定位是哪一层的问题。
